# Publishing this project

The goal is a link colleagues can open to see what the tool does, and a repository other
labs can install from, without any patient recording ever leaving a lab machine.

The arrangement that achieves both:

| | where it runs | what data it sees |
|---|---|---|
| **Published demo** | Streamlit Community Cloud, public | synthetic recordings only |
| **Real analysis** | the lab's own machine | real recordings, never uploaded |

---

## The one rule

**A published app can only read files that are in the repository.** Recordings, the manifest
and the outputs are all gitignored, so a deployed copy has no patient data available to it,
it falls back to the synthetic demo set automatically.

That means the risk is not the app. It is the *repository*. Everything below is about keeping
the repository clean.

---

## Before publishing, every time

```bash
python src/check_before_publish.py
```

It looks at what git would actually commit, not at what `.gitignore` is supposed to say,
and refuses if it finds recordings, the manifest, or a subject code. It exits non-zero on a
problem, so it also works as a pre-commit hook:

```bash
echo 'python src/check_before_publish.py' > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

### What must never enter the repository

| | why |
|---|---|
| `data/raw/` and any `*_eventonly.csv` | the recordings themselves |
| the NIDAQ manifest workbook | participant IDs against session dates |
| `docs/Pharma-rundown.xlsx` | roster with clinical notes |
| `docs/Table-layout.csv` | holds one subject's measurements |
| `outputs/` | results carry subject codes |
| `report.txt` | names session folders |
| `docs/*.pdf` | journal articles cannot be redistributed |

### Subject codes in source

A bare code such as `P1Sxx` is pseudonymous and low risk. A code *with a session date*,
`P1Sxx_..._02152023-13-35-50`, says that person had a session at that moment, which in a
19-person study is meaningfully re-identifying.

So the tests and figures find recordings **by protocol**, never by filename:

```python
csv = sorted((ROOT / "data" / "raw").glob("*_TMS_120_*.csv"))[0]
```

The pre-publish check enforces this.

## Publishing the demo

```bash
python src/make_demo_data.py      # generates data/demo/, synthetic, safe to commit
python src/check_before_publish.py
```

Then push to GitHub and, at [share.streamlit.io](https://share.streamlit.io), point Streamlit
Community Cloud at the repository with `app.py` as the entry point. It installs from
`requirements.txt` automatically.

The deployed copy detects that `data/raw` is absent and switches to **demo mode**:

- a banner stating the recordings are synthetic;
- the folder box disabled, on a public host, a free-text path would let any visitor read
  files on the server.

**Never upload real recordings to the deployed instance.** It is a demonstration. Anyone
wanting to process real data installs locally.

### What the demo data is

Generated by `src/make_demo_data.py` from a fixed seed: random noise plus a response drawn at
a chosen latency. It is not derived from any recording. It also covers three things the real
sample cannot: a nested session folder, a paired recording firing two triggers, and a
contracting muscle: so `src/tests/test_demo_data.py` checks the pipeline recovers the values
each file was built with.

## Sharing a self-check report

```bash
python src/selfcheck.py --data <YOUR FOLDER> --anonymise > report.txt
```

The report holds counts, protocol names and millisecond values: no EMG samples. Without
`--anonymise` it also prints session folder names, which are subject codes plus dates: fine
inside the lab, not for sharing more widely.

## For a lab that wants to run its own data

```bash
git clone <repository>
cd SCISoftwareIntern
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
streamlit run app.py
```

With no data present it opens in demo mode. Adding recordings to `data/raw/`, or setting
`data_root` in `config/params.yaml`, switches it to the real thing, on their machine, under
their own approvals.

---

## What this does not cover

Hosting real recordings anywhere, including on an institutional server. That is an IRB and IT
decision rather than a code change, and nothing here should be read as approval for it.
